## Objective
Add mouse text selection and Ctrl+C copy across the TUI, and move Stop off
Ctrl+C without losing a reliable way to cancel a streaming run.

## Completed
- Added `SelectableStatic`, a `Static` subclass that applies cell offsets and
  implements `get_selection` for Rich visuals. Its class docstring records why
  we keep the MIME-aware Rich Markdown/Syntax/Group rendering instead of
  migrating to Textual's native Markdown widget.
- Applied it to all free-standing TUI text: transcript bodies, status and
  inspector panes, app chrome, dialogs, HITL prompts, turn status, sessions
  previews, and the agent status/project-root slots. Interactive control labels
  (buttons, list items, collapsible titles, radio/select options) remain
  controls.
- Transcript message expansion now distinguishes click from drag: a drag selects
  text and suppresses the expand/collapse toggle; the overflow hint mentions
  drag-to-select.
- Key bindings: Ctrl+C copies (Textual's Screen action); Ctrl+Shift+C stops a
  run; F12 is the fallback for terminals that intercept Ctrl+Shift+C. Ctrl+X is
  not used because it is TextArea's cut binding.
- Updated TUI docs, the selection decision note, and the changelog. Added pilot
  tests for drag/copy, drag-vs-click, status/inspector extraction, app chrome,
  and the new stop/copy keys.
- E2E follow-up:
  - `RichVisual` ignores Textual's selection render options, so markdown,
    syntax and grouped bodies had no selection highlight. `SelectableStatic`
    now applies the selection background to the selected cell span itself and
    pads blank lines so a drag can start or end there. The theme selection
    foreground is overridden to `$text` for plain Content selections.
  - Copy now also tries `wl-copy`/`xclip`/`xsel`/`pbcopy`/`clip` after Textual's
    OSC 52 copy and shows a `Copied N characters` notification. This fixes
    terminals that ignore OSC 52, where the app copied internally but the OS
    clipboard never received the text.

## Errors and Lessons
- Textual supports selection generally, but Rich renderables hosted in a plain
  `Static` are wrapped in a `RichVisual`, which has no cell-offset selection and
  returns no text from the default `get_selection`.
- Native Textual `Markdown` selection only covers some block types (centered
  headings do not extract correctly) and would require rewriting the MIME-aware
  renderer; the decision is recorded in `SelectableStatic`.
- A simple click clears the screen selection before `Click`, while a drag keeps
  it, so checking `screen.selections` cleanly separates expand/collapse from
  selection.
- Ctrl+X cannot be a global fallback while a TextArea is focused; F12 works and
  is reported by terminals.
- Copy uses OSC 52 plus a best-effort system clipboard tool. OSC 52 alone is
  terminal-dependent (macOS Terminal and some configured emulators ignore it);
  a remote/SSH session can only use OSC 52 or native terminal selection.
- Blank Rich lines have no cell-offset segments; pad them before applying
  offsets or a drag ending on an empty line becomes `end=None`/select-to-end.

## Open Questions
- Revisit a native-Markdown migration if Textual gains selection support for
  `RichVisual` or if the rendering/test churn becomes worthwhile.
- Whether to make interactive control labels selectable; currently they remain
  controls by design.
- Rich Markdown centers H1 headings, so a drag from the left edge selects
  leading layout spaces; left-aligning H1s or trimming leading whitespace is a
  deferred polish item (`devdocs/backlog.md`).
