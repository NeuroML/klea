## Objective

Fix two reported terminal UI (TUI) symptoms: sustained CPU usage during long sessions, and a truncated token in the path-approval preview. Add regression coverage for the TUI behaviours touched.

## Completed

- Status panel reconciliation in the TUI is now signature-guarded, so an unchanged status does not trigger repeated rebuilds of the pane; this removes the steady CPU load observed in long sessions.
- Path-approval preview now recovers a truncated token by anchoring on the token text instead of taking a fixed character slice, so the detected path/token is shown intact.
- Transcript rendering uses a bounded window with explicit scroll-up and scroll-down paging plus a hard cap on mounted widgets, so very long transcripts no longer grow the mounted tree without limit.
- The thinking/working spinner is stopped on any non-terminal stream exit (error or cancellation), not only on a clean finish, so it cannot keep animating after a run ends.
- Added `utils_pkg/tests/ui/tui/test_tui_regression.py` covering the status-panel signature guard, the preview token recovery, the bounded transcript paging/cap and the spinner stop on non-terminal exit.
- Updated `devdocs/system/tui.md` to document the status reconciliation, paging and preview behaviour.

## Errors and Lessons

- Comparing whole rendered output to decide whether to repaint is expensive in a long session; a cheap signature of the underlying state is the reliable guard against redundant work.
- A fixed-width slice of a free-form preview string can cut the meaningful token; recovering by anchoring on the token is more robust than widening the slice.
- Keeping every rendered item mounted does not scale with transcript length; a windowed view with an explicit cap keeps memory and CPU bounded.

## Open Questions

- Whether the mounted-widget cap should be configurable per deployment, and what default suits very large sessions.
- Whether other panes (inspector, dialogs) need the same signature-guarded reconciliation as the status panel.
