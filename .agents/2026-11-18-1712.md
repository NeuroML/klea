## Decision

The per-run `transcript.jsonl` of the eval harness is a **reduced per-turn
record**, not a verbatim conversation log. One JSON line per executed case turn
carries only six fields: `turn_number`, `role`, `input`, `output`, `status` and
`error`. The record exists so that a stored run can be reconstructed and a
failed run explained after the fact. Everything else the harness already keeps
- run identity in `run.json`, and per-turn usage, latency, tool-call counts,
scores and resolved models on the `metrics.jsonl` line -- is deliberately not
repeated in the transcript.

## Rationale

- **Diagnosis, not replay.** The transcript answers "what was this run asked
  and how did it answer" when a stored result needs explaining. That is what
  the six fields give; verbatim system prompts, replayed history and tool
  payloads do not add to that question.
- **Scoring must stay reproducible from the stored run.** ADR-0061 makes
  grading deterministic and reproducible from `run.json` and `metrics.jsonl`
  alone. `scoring.py` therefore keeps reading only `expected_outputs` and
  `tool_expectations`; the transcript is never a grading input, so no graded
  field can drift with it.
- **No second copy of the metrics.** The turn's usage, latency, tool-call
  counts and scores already travel on the `metrics.jsonl` line (ADR-0058).
  Duplicating them in the transcript would only create two sources of truth.

## Rejected scope

- **Full turn fidelity** (system prompts, replayed history, tool payloads) was
  rejected: debugging belongs to the regular development workflow and the
  `~/.local/share/klea-*` logs, not to a stored run artefact.
- **Transcript-fed re-grading** was rejected for the same reason ADR-0061
  rejects LLM-as-judge gating: the transcript is not a grading input, so a
  graded verdict must remain derivable from `run.json` and `metrics.jsonl`.
