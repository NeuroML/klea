**Authoring agent:** opencode

## Objective
Add surrounding-line context to the bundled `grep` tool so the LLM usually
gets enough code to avoid a follow-up `read_file`.

## Completed
- `b411a4a4` In-house grep returns grouped per-file hunks
  (`{path, start_line, end_line, lines}` with `{line_number, line, match}`),
  merging overlapping windows and counting context toward `max_chars`.
- `d9c19fb9` Ripgrep backend uses `-C <n>`, parses `context` JSON records,
  groups contiguous records into hunks, and sizes the stdout cap for context.
- `3585513b` Exposed `context_lines` (default 2, range 0-7) through `grep()`
  and the bundled MCP tool; values above 7 are clamped internally.
- `fd8c9c0e` Documented the hunk contract in `devdocs/system/file-tools.md`,
  updated user docs, `CHANGELOG.md`, and the backlog reference.
- Shared helpers live in `klea_utils/mcp/tool_impls/grep_hunks.py`.

## Errors and Lessons
- Initial truncation logic included trailing context after the match cap,
  which could label real matches beyond the cap as `match: false`.  Fixed by
  clamping the final hunk to the last returned match in both backends.
- `DEFAULT_MAX_CHARS` was moved to `grep_hunks.py` to avoid duplicating the
  shared character budget across backends.
- Another agent was editing `agent_pkg/` concurrently; its changes were left
  untouched and only explicitly scoped files were staged.

## Open Questions
- Whether the default of 2 context lines is sufficient in practice needs
  evaluation data; the tool now allows up to 7.
- Ripgrep match byte offsets are still ignored (backlog Phase 2 for
  `read_file` region reads).
