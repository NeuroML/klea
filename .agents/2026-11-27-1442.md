## Objective

Extend the `klea-eval` harness so it consumes the per-call LLM usage and the
evaluator-retry signals the Klea server already streams, carries them per turn,
per run and per suite, exposes them through `klea-eval summary`, and documents
them.

## Completed

- The HTTP runner now reads, from the `usage` event's `data.details`:
  `llm_calls` and the per-invocation `llm_usage` entries, and derives
  `peak_context_tokens` as the largest input-plus-output token count over a
  turn's calls.
- The HTTP runner now reads, from the `inspect` event's `data.details`, the
  `kind: "evaluator_retry"` retries (with `plan_step`, `attempt`,
  `max_attempts`) and a `verdict` marker, and records `evaluator_retries`,
  `evaluator_retry_count`, `max_attempt_seen` and `first_try`.
- `metrics.py` parses and aggregates those fields per turn, per run
  (`llm_calls`, `per_call_usage`, `peak_context_tokens`,
  `evaluator_retry_total`, `first_try_passes`, `recovered_after_retry`,
  `first_try_pass_rate`, `max_attempt_seen`).
- `scoring.py` carries the same fields onto `CaseScore` and `SuiteAggregate`
  and serialises them in `to_dict()`.
- `klea-eval summary` prints `llm_calls`, `peak_context_tokens`,
  `evaluator_retry_total` and `first_try_pass_rate`, with `n/a` for an absent
  peak or an ungraded suite.
- Docs: the eval guide gains a `Reading the run metrics` section; CHANGELOG,
  the backlog and the node-contract glossary were updated.

## Errors and Lessons

- The `summary` CLI tests initially monkeypatched `suite_summary` on the
  `ui.cli` module, which failed because `cli` imports it lazily from
  `klea_eval.api`.  The fix patches `api.suite_summary` instead; a lazily
  imported name must be patched at its defining module, not the importing one.
- `ty check` reports pre-existing diagnostics in `agent_pkg`, `mcp_pkg` and
  `utils_pkg` that are unrelated to this change; `ruff` and the eval test
  suite are clean (485 passed, 1 skipped).

## Open Questions

- Only the first retried step of a batch carries the `evaluator_retry` detail
  on the backend, so `evaluator_retry_total` under-reports a batch that
  retried several steps.  Whether the backend should report every retried step
  remains open.
- A stable node key for per-node usage aggregation is still missing.

## Notes

- Per-call usage is stored as a tuple of plain mappings (``tuple[dict, ...]``)
  both side of the JSON boundary: reading skips non-mapping entries rather
  than raising, so an older record still aggregates.
- `peak_context_tokens` is a retry-merged upper bound: it spans every call a
  turn made, retried calls included, so it is not the context size of a single
  attempt.
- `first_try` is `true` when a verdict was seen with no retries, `false` when
  any retry was recorded, and `null` when the stream carried neither.
- `first_try_pass_rate` is `null` on a zero denominator (no graded turn), so a
  missing value never reads as `0.0`; the suite averages per-case rates so a
  case with many turns does not outweigh one with a single turn.
- There is no suite-level `per_call_usage` field: the entries live per turn and
  per run only, keeping the suite aggregate compact.
- Commits: `feat(metrics): consume per-call LLM token usage and peak context
  from usage events`, `feat(metrics): consume evaluator-feedback retry signal
  from inspect events`, `docs(eval): document per-call usage and
  evaluator-retry metrics`.
