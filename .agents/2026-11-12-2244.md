**Authoring agent:** opencode

## Objective

Fix chat titles that stayed stuck at a slug-derived name, and renames that
silently did nothing, in both the TUI and the web UI.

## Completed

- Diagnosis: both UIs did read the stored title back, but every chat was born
  with a slug-derived title (`ui/state.py::ensure_chat`,
  `ui/client.py::create_chat_on_server`, `api/sessions.py::create_chat`), and
  renames failed silently: `rename_chat_on_server` never checked the PATCH
  status and `SessionStore.rename_chat` discarded the rowcount, so a zero-row
  update still reported success. The defect was shared by the TUI and the web
  UI.
- Commit A `8353c2a2` - `fix(ui): stop deriving chat titles from the chat slug`:
  empty seed name, only `chat_id` posted on create, no coolname slug
  substitution, raw title stored, `_display_title` used as a read-time
  fallback. Tests: `tests/test_client_chat_titles.py` and
  `test_sessions_db.py::test_create_chat_stores_an_empty_title`.
- Commit B `53f41679` - `fix(ui): surface chat rename failures instead of
  ignoring them`: the client now returns a bool and logs an error on non-2xx,
  `rename_chat` is rowcount-based, `update_chat` returns 404 on zero rows, the
  web UI shows a negative notification and refreshes only on success, and the
  TUI notifies and refreshes its header/picker only on success. Tests:
  `tests/test_client_rename.py`, `TestSessionsRename`,
  `test_rename_chat_reports_missing_chat`, plus the updated stale TUI test
  `test_status_panel_shows_chat_name`. `devdocs/system/tui.md` and
  `CHANGELOG.md` were updated in the same commit.
- Verification: 280 passed / 2 skipped, ruff clean, `ty` at the pre-existing
  38-diagnostic baseline.

## Errors and Lessons

- A rename path that ignores its write result turns a hard failure into a
  silent no-op; check status codes and rowcounts at every layer.
- Titles derived from identifiers look plausible enough to hide the bug, so
  seed the name empty and render a fallback at read time instead.
