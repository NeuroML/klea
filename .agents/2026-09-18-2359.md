### Design A: Planner owns the whole plan

Live evidence showed the real T3/T6 damage came from *code*, not the model:
`Planner._update_state` re-applied `done` by matching step numbers across
plans, so a renumbered replan collided an old done step `1` with a new step
`1`, forcing it `done`, leaving `current_step_index` out of range while
`step_outputs` were cleared -- an unrecoverable picker loop.

- `Planner._update_state` no longer mutates the plan; the model authors
  statuses and `current_step_index`.
- `PlanSchema.validate_plan()` validates structure
  (positive/unique numbers, in-plan `depends_on`, in-range index).
- Generic node validation-retry loop in `AbstractLLMNode.execute`
  (`max_validation_retries`, `validation_feedback` prompt var);
  `Planner._validate_result` uses it, then fails closed to `unplannable`.
- Prompt trims (removed picker bullet and evaluator "exact" bullet) plus the
  planner ownership contract, the read-only rule, and "early exits have equal
  value".

### Evaluator-terminal `abort`

T6 re-ran still burning five replans on an impossible goal, all `need_replan`.

## Errors and Lessons

- **Do not add prompt rules for machine-checkable invariants.**  Each failing
  task initially produced a new prompt bullet; that does not scale.  Push
  consistency into schema validation + fail-closed handling; reserve prompts
  for judgement.
- **Do not let code patch model output positionally.**  Matching plan steps by
  number across revisions is brittle exactly when the model renumbers -- the
  case it was meant to protect.  Let the sole author own the whole object and
  validate it.
- **Plan similarity is not deterministically checkable.**  There is no sound
  way to detect "the last N plans were the same" (wording/step count vary), so
  the unreachable-goal guard was placed where judgement already lives (the
  Evaluator), not in a plan-comparison heuristic.
- **Absence handling is a general model failure mode.**  Missing-file requests
  draw agents to fabricate or over-search (opencode/deepseek v4.1 tried
  `find /`); treat it as a class, not a one-off.
- HF rate limiting causes intermittent blank structured responses; the retry
  now fires (2/2) but a weak model may not recover in-window.  Fail-closed and
  honest is the correct outcome, not a bug.

## Later (same session): models.dev provider endpoints

- Added `provider:<model>` support: for models.dev catalog providers the
  endpoint is resolved from the catalog, so no `custom:<model>:<url>` is
  needed.  `get_provider_endpoint(provider, model_name)` returns `(api, npm)`;
  `resolve_catalog_provider_endpoint` maps npm -> wire surface and reuses the
  existing OpenAI/Anthropic branches.
- Wire surface is resolved **per model**, not per provider: gateways such as
  OpenCode Go/OpenRouter serve different models on different APIs and the
  catalog records a per-model `provider.npm` override.
  `@ai-sdk/openai` -> Responses, `@ai-sdk/anthropic` -> Messages,
  `@ai-sdk/openai-compatible`/vendor packages -> Chat Completions; non-OpenAI
  npm (`@ai-sdk/google`, ...) is left to LangChain.
- `huggingface`/`anthropic` keep native handling: `huggingface` is excluded
  from catalog lookup (`MODELS_DEV_PROVIDERS_IGNORED`, one entry; `anthropic`
  is covered by the no-`api` guard).  Catalog `env` is ignored (npm-specific);
  the OpenAI surface uses `OPENAI_API_KEY`.
- Only `langchain-openai` is needed for catalog providers, not per-provider
  integration packages.
