## Objective
Ship the per-session stores config transport end to end: how a configured
stores file travels from the host app through `ClientContext` and tool-call
metadata into the stores MCP tool, plus validation and defaulting rules.

## Completed
- Versioned request-metadata key `klea/stores-config-path/v1` in
  `utils_pkg/klea_utils/stores/utils.py`, so the payload shape can evolve
  without breaking older callers.
- Transport plumbing: session config carried in `ClientContext`, sent as
  tool-call `_meta` metadata, and forwarded through MCP dispatch into the
  bundled stores tool.
- Precedence for resolving the stores config, highest first:
  1. a lifespan-reserved value (reserved for server-side wiring and not
     overridable by request metadata)
  2. the request `_meta` payload (`klea/stores-config-path/v1`)
  3. the `KLEA_STORES_CONFIG_FILE` environment variable
  4. otherwise fail closed
- Fail-closed validation: a configured stores path that does not exist or is
  otherwise invalid raises instead of silently falling back, so misconfigured
  deployments surface immediately (`test_stores_config_resolver.py`).
- Host default is agent-only: the host app default is wired in the agent
  package config; the RAG app is deliberately left unchanged and keeps its
  existing behaviour.
- Developer documentation synced in
  `devdocs/system/stores-domain-search-tool.md`.

## Errors and Lessons
- `test_plogging` is known to fail in some environments for pre-existing,
  environment-sensitive reasons unrelated to this work. Do not treat it as a
  regression signal for the stores-config changes.
- Silent fallback on a bad stores path hid configuration mistakes; fail-closed
  behaviour is the safer default for deployment-time config.

## Open Questions
- Should the RAG app ever adopt the same per-session stores config, or is the
  agent-only default intended to stay?
- Is the versioned metadata key worth bumping, or is additive evolution within
  the current version sufficient?

## Notes
- The feature is split by layer: config resolution, context transport,
  metadata serialisation, MCP dispatch, and the store tool itself. Future
  changes should touch the matching layer rather than bypassing it.
