## Objective

- Concurrent backends against one SQLite checkpoint DB fail with opaque `database is locked`
  errors; the multi-backend-per-storage-root model had to be replaced with a safe single-writer model.
- MCP stdio tool servers spawned with the wrong context and leaked state between sessions, so
  tool-server isolation and env/cwd plumbing were required.
- Decide the long-term checkpoint storage layout (A1/A3 hardening vs. A2 routing) and record it in
  the ADR.

## Completed

- `04a371f5`  ---  B2b: per-session MCP client pool with LRU eviction and deterministic teardown on
  session delete; per-session MCP server isolation delivered.
- ADR-0023 amended: one backend per storage root is the supported model, with A3 (advisory lock,
  owner identity, stale detection, fail-fast loser behaviour) as the policy and A1
  (`journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout`) making restart/auto-spawn windows safe;
  A2 per-thread checkpoint routing recorded as considered-and-rejected.
- `KLEA_AGENT_HOME` confirmed as an opt-in relocation/isolation escape hatch only, never a
  concurrency mechanism.
- Per-client cwd/env isolation explicitly deferred to a follow-up (design proposal kept in Notes).
- Both commits passed `ruff`, `ty`, `pytest` and the review gates; no other production code changed.

## Errors and Lessons

- B2a/B2b did not fix the reported symptom: two TUIs still get servers running the backend's
  environment  ---  a missing feature, not a regression.
- Upstream LangGraph SQLite savers set WAL only (no `busy_timeout`, no cross-process mediation), so
  contention must be handled in our own connection layer.
- A shared/global MCP client leaked state between sessions; per-session lifecycle fixed that but not
  per-client cwd/env isolation.
- A2 (proxy saver, per-backend files) solved the wrong problem  ---  making N backends safe on one file
   ---  and would need permanent maintenance plus reconciliation plumbing; rejected.
- `KLEA_AGENT_HOME` does not protect two backends deliberately pointed at the same home, the likely
  mistake; safety has to come from A3 + A1, not from path configuration.

## Notes  ---  design proposal for the next session: client-supplied `cwd`/`env` (loopback only)

Confirmed: B2a/B2b did **not** fix the reported symptom. They delivered per-session MCP *process*
isolation (one MCP client + one `mcp.server.bundled` process per chat session, LRU eviction, teardown
on session delete) but use the **backend's** env/cwd/interpreter for every spawn, because
`graph/base.py` delegates to `spawn.bundled_server_config` with `env`/`cwd`/`interpreter=None`. Two
TUIs therefore get two servers running the *same* environment: a missing feature, not a regression.
What B2a therefore bought is the contract needed to fix it -- `bundled_server_config(*, env, cwd,
interpreter)` already accepts an explicit env (caller wins; `VIRTUAL_ENV`/`PYTHONHOME`/`PYTHONPATH`
stripped from the inherited part) and cwd -- so the remaining work is getting a *client-supplied*
context to that call.

### (1) API surface

Optional `client_context` object on the **chat/session-creation** request (`utils_pkg/klea_utils/api/sessions.py`;
the exact route/schema was not inspected this session, so names are proposals):

```json
{"client_context": {"cwd": "/tmp/projA", "env": {"VIRTUAL_ENV": "/tmp/projA/.venv"}, "interpreter": "/tmp/projA/.venv/bin/python"}}
```

All fields optional; absent/`null` => today's behaviour. Context is set **once at chat creation and
immutable for that chat** (no per-request trust decisions; consistent with `thread_id`-keyed pooling).
A TUI relaunched with a different `--cwd` creates a new chat (or forces a pool respawn, see 4). No new
endpoint needed. Add a capability flag to the health/info endpoint (e.g. `client_context: "loopback"
| "remote" | "disabled"`) so the TUI knows whether to send it.

### (2) Security constraints

- **Loopback-only by default.** Accept only when the request socket peer (`request.client.host`) is
  `127.0.0.1`/`::1`; otherwise 403 `client_context_requires_loopback`. Remote use requires explicit
  opt-in `KLEA_ALLOW_REMOTE_CLIENT_CONTEXT=1` (default off), documented as handing the client
  arbitrary-code-execution-equivalent control over spawned tool servers.
- **Trust framing:** the client context selects the cwd/env of a spawned child process, i.e. what code
  that child imports/runs. Loopback peer == same OS user session, the only acceptable trust boundary;
  there is no per-user auth in the SQLite/local path today.
- **No credential leakage:** never log `env` values (log key names only); do not persist env into
  `checkpoints.db`; it goes only to the session store and is dropped with the chat.
- **Bounded input:** reject `len(env) > 64` or serialised size > 8 KiB; reject names containing
  `=`/NUL or empty, values containing NUL; `cwd` must be absolute, exist, be a directory, be
  readable/executable; resolve symlinks before storing. Optional `KLEA_CLIENT_CWD_ROOTS` to constrain
  allowed roots (unset = any).

### (3) Backend validation logic

New general-purpose helper module (per the split-helpers rule), e.g.
`utils_pkg/klea_utils/client_context.py`: `validate_client_context(raw, *, peer_host, allow_remote,
cwd_roots) -> ClientContext | None`, raising a typed error mapped to 403 (peer/setting) or 400/422
(malformed). Order: flag/peer check -> type check -> bounds -> `cwd` resolution -> env sanitisation.
Reject outright rather than silently dropping, so a TUI cannot believe isolation is active when it is
not.

### (4) Storage and plumbing to the spawn

- Persist as a nullable `client_context` JSON column on `chat_sessions` in `sessions_db.py` (migration
  + delete with the chat; `delete_chat` already exists). Not in the checkpoint DB, so a restored chat
  without the TUI's machine does not resurrect a stale path.
- `SessionMCPClients.get(session_id, client_context=None)` gains the argument; each pool entry stores a
  **fingerprint** (hash of cwd+interpreter+env) and the context. On a fingerprint mismatch, close the
  existing client and immediately recreate (covers resume-with-different-`--cwd`). LRU/idle/TTL/
  `aclose*` semantics unchanged.
- `dispatch_tool_calls`/`ToolsCallerNode` already carry `session_id`; extend `_session_id_for_dispatch`'s
  caller to load the stored context for that session and pass it to `pool.get(...)`. The pool then
  builds the spawn config with `bundled_server_config(env=..., cwd=..., interpreter=...)` -- exactly
  the B2a contract, so B2a needs no change.
- Fallback chain when nothing is supplied: backend-probed env -> `none` (current behaviour),
  preserving non-TUI callers and tests.

### (5) Implementation steps

(a) `client_context.py` validator + tests (loopback accept, non-loopback 403, remote opt-in,
malformed cwd/env rejected, bounds). (b) Pydantic `ClientContext` + optional field on chat-create
request; store/read/delete in `sessions_db.py` with migration. (c) Pool: accept/store/fingerprint
context, respawn on change + tests. (d) Wire dispatch/tools_caller to resolve and pass it. (e) TUI:
`--cwd` (default `os.getcwd()`), `--env KEY=VALUE` (repeatable) and/or `--forward-env` opt-in; send at
chat creation; skip with a warning when the health flag says not allowed. (f) Health capability flag.
(g) Tests incl. E2E: two TUIs with different `--cwd`/venv => two `mcp.server.bundled` PIDs whose
`/proc/<pid>/cwd` differ and whose `environ` matches each client's explicit env. (h) Docs/ADR
amendment recording the loopback trust boundary and the immutability decision.

**Sequencing:** follow-up to B2a/B2b, independent of A1/A3; own commit(s) after the current three.
