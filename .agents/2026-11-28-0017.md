## Objective
Fix `--continue` (TUI and web) resuming the most recently *created* chat instead of
the most recently *used* one: persisting a message never advanced the chat's
last-activity timestamp.

## Completed

- Root cause, `SessionStore` (`utils_pkg/klea_utils/api/sessions_db.py`): `chat_sessions.updated_at`
  was only written by `create_chat`, `rename_chat` and the override helpers. Message
  persistence (`add_message` / `add_messages`) never touched it, and the dedicated
  `touch_chat` helper has no call sites. `list_chats` already sorts by
  `ORDER BY cs.updated_at DESC` (and `--continue` opens the first row), so the write
  side was the only thing missing.
- Fix location, same module: `add_message` and `add_messages` now run an inline
  `UPDATE chat_sessions SET updated_at = ? WHERE user_id = ? AND chat_id = ?` inside
  their existing `with self._lock:` block, alongside the message INSERT/`executemany`
  and before the single `commit()`, reusing the batch's `now`. This keeps one
  transaction and one commit per turn and needs no new log line.
- Deliberately rejected the alternative of calling `touch_chat`: it re-acquires the
  lock and would add a second connection round-trip / commit per persisted message.
  The inline UPDATE is a no-op if the `chat_sessions` row is absent, which is safe
  because both run paths (`run_query`, `stream_response` in `chat_core.py`) call
  `create_chat` (`INSERT OR IGNORE`) before persisting.
- Regression tests added to `utils_pkg/tests/test_sessions_db.py` (existing `store`
  fixture, no existing test modified):
  `test_add_message_bumps_updated_at_so_continue_picks_the_last_used_chat` (an older
  chat that just received a message outranks a later-created unused chat in
  `list_chats`) and
  `test_updated_at_stays_at_creation_time_until_a_message_is_persisted`.
- Docs updated to match the behaviour: `devdocs/system/tui.md` and
  `devdocs/adr/0050-textual-tui.md` now say `--continue` resumes the most recently
  *used* session (newest `updated_at`, advanced by message persistence, a rename or a
  model-override change). No `docs/` page documents the ordering, and the CLI help
  text already said "most recently updated chat session".
- `CHANGELOG.md`: one bullet appended to the `### Fixed` group of
  `## Unreleased  ---  klea_utils / klea_rag` describing the corrected `--continue`
  ordering.

## Errors and Lessons

- `ty check` (repo root) exits non-zero with 40 diagnostics; all are pre-existing and

  `test_chunk_worker.py` optional lists, etc.). None fall in the touched lines of
  `sessions_db.py` / `test_sessions_db.py`.
- Lesson: an ordering bug can live entirely on the write side -- the `ORDER BY` was
  already correct, so the store's invariants (`updated_at` = last activity) had to be
  restored at persistence time rather than by changing the query or adding a
  tie-breaker.
