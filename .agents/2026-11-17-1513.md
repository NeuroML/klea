## Objective

Make the interactive path permission ask easier to read: instead of a flat list of
requested paths with the plan-step context detached at the top of the form, group
each requested path under the plan step whose work it serves.

## Completed

- Grouped the permission ask by plan step in both frontends: the web permission
  form (`chat_area.py`) and the TUI permission panel (`hitl.py`).
- Each request is placed under the heading of the lowest plan-step number it
  serves, in ascending step order; the row keeps its payload order, its 1-based
  display number and its `path`/`directory` decision key.
- A request that serves several steps sits under its lowest step and gains a
  bounded `Also serves step N` hint listing the rest.
- Requests with no step context go to a trailing `Other paths` bucket, emitted
  only when at least one request carries step context.
- When no request carries step context the previous flat layout is kept, so older
  checkpoints and plan-less runs (for example Klea RAG) are unchanged; step
  context hoisted onto the ask alone still renders as the legacy top-of-form
  lines.
- Boundary was not relaxed: no change to the permission payload, the decision
  keys, the detection tiers, or the interrupt protocol. Summaries stay
  whitespace-collapsed, cut to 160 characters with an ASCII `...`, and the
  hoisted step list stays capped at 8 entries.

## Errors and Lessons

- The TUI submit path reads decisions by radio widget id, so the grouping had to
  keep `perm-{index}` ids tied to the global 1-based position rather than the
  per-group position; the grouped layout preserves numbering and only the
  iteration changes.
- The web form already re-renders its rows on select, so the grouping is computed
  once at form build time; choices stay on the stored ask, so a re-render cannot
  lose an in-progress decision.
- Both frontends must fall back to the flat layout: an older checkpoint can carry
  step context on the ask with none per request.
- `ty check` is not a clean gate in this repo today, so its exit code cannot be
  used on its own to judge a change; the diff and the tests were the signal.

## Open Questions

- Should a request that serves several steps instead be repeated under each step
  heading? Current choice is one placement plus an `Also serves step N` hint, to
  keep one decision control per path and one decision key per path.
- Should the `Other paths` bucket be omitted entirely, or labelled differently,
  when most requests lack step context?
